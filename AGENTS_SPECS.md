SalesAgent (Orchestrator)
SalesAgent serves as the central orchestrator of the platform, receiving all customer inputs and routing them to the appropriate worker agents based on intent. It is triggered on every customer interaction and takes customer ID, query, budget, and channel as inputs. It coordinates StylingAgent and RecommendationAgent for discovery, PaymentAgent for purchase, StoreReservationAgent for in-store booking, and FollowUpAgent for post-purchase engagement. On payment failure, it automatically escalates to HumanSupportAgent without requiring manual intervention. It also manages channel switches via SessionManager, ensuring context is never lost across touchpoints.

StylingAgent
StylingAgent is triggered at the start of every recommendation flow to detect the customer's style intent from their query. It takes the raw customer query as input and returns a style category — casual, formal, partywear, or sportswear. It uses all-MiniLM-L6-v2 embeddings to compute cosine similarity against predefined style descriptions. If confidence falls below 0.3, it falls back to Groq LLM for classification. On Groq failure, it defaults to "casual" to ensure the flow never breaks. The detected style is passed to RecommendationAgent to enhance search quality.

RecommendationAgent
RecommendationAgent is triggered after style detection to find the most relevant products for the customer. It takes customer ID, query, budget, and style as inputs and returns up to 5 filtered product recommendations. It uses a hybrid approach — semantic search via ChromaDB and MiniLM for meaning-based retrieval, combined with TF-IDF cosine similarity for keyword precision. Results are filtered by budget, customer dislikes from PreferenceLayer, and stock availability from InventoryAgent. Each recommended product receives a unique natural language justification generated by Groq LLM. On Groq failure, a templated reason is returned as fallback.

InventoryAgent
InventoryAgent is triggered during the recommendation filtering process and whenever a customer requests a stock check. It takes customer ID and SKU as inputs and returns availability status and total stock count across all sizes. It reads directly from inventory.json, summing stock across size variants. If a SKU is not found in inventory, it returns available as false with zero stock, ensuring out-of-stock products are never recommended. It has no external API dependency and therefore no escalation path — all failures are handled by returning unavailable status.

PaymentAgent
PaymentAgent is triggered when a customer confirms a purchase. It takes customer ID and amount as inputs and simulates a payment gateway returning one of three statuses — success, upi_failure, or bank_timeout. Each failure status includes a specific recovery suggestion: UPI failure prompts the customer to try a card, while bank timeout suggests retrying after a few minutes. On any failure, SalesAgent automatically escalates to HumanSupportAgent with the failure type as context. Payment status is saved to SessionManager so FollowUpAgent can reference it during post-purchase communication.

StoreReservationAgent
StoreReservationAgent is triggered when a customer wants to reserve a product for in-store pickup, typically during the WhatsApp to in-store journey. It takes customer ID and SKU as inputs and returns a reservation confirmation with store name and 24-hour pickup window. It calls Groq LLM to generate a warm, personalized confirmation message specific to the reserved product. On Groq failure, a standard confirmation message is returned. It does not check inventory independently — inventory validation is handled upstream by RecommendationAgent before reservation is offered.

FollowUpAgent
FollowUpAgent is triggered after a purchase attempt to send a personalized post-purchase message on the customer's current channel. It takes customer ID as input and reads payment status and current channel from SessionManager. If payment succeeded, it generates a thank-you message encouraging further exploration. If payment failed, it generates a recovery-focused message helping the customer complete their purchase. All messages are generated by Groq LLM with full context of payment status, channel, and purchased items. On Groq failure, appropriate hardcoded fallback messages are returned for each scenario.

HumanSupportAgent
HumanSupportAgent is triggered automatically by SalesAgent whenever a payment failure occurs. It takes customer ID and issue type as inputs and returns an escalation confirmation with an empathetic message specific to the issue. It calls Groq LLM to generate a response tailored to the failure type — UPI failure receives a different message than bank timeout. This ensures customers feel heard rather than receiving a generic error message. On Groq failure, a standard escalation message is returned. It represents the human-in-the-loop override mechanism required by the platform's trust framework.

CartMonitoringAgent
CartMonitoringAgent tracks items added to cart, monitors cart state, and detects abandonment. It is triggered when a customer adds a product to cart or when the system checks for inactive carts. It takes customer ID, SKU, product name, and price as inputs for cart operations, and customer ID alone for abandonment checks. It reads SessionManager to determine if payment was attempted — if cart has items but no payment was attempted, abandonment is flagged and Groq generates a personalized reminder message. Cart totals are recalculated on every quantity update. On Groq failure, a standard reminder is returned.
